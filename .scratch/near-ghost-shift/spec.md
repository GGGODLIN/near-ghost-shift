## Problem Statement

In multi-agent swarms and autonomous business workflows on NEAR, a coordinator delegates a paid task to an active worker agent (`worker-a.ghostshift.testnet`). When `worker-a` stalls, loses network connectivity, or hits a provider timeout, its lease expires and a backup worker (`worker-b.ghostshift.testnet`) takes over to complete the job. Shortly afterward, the stalled "zombie" `worker-a` recovers and submits its late result or triggers a delayed settlement callback using a still-valid cryptographic key. Without an on-chain monotonic fencing token and asynchronous verification gate, `worker-a`'s stale write overwrites `worker-b`'s accepted artifact, corrupts downstream state, or triggers double bounty payouts (the classic distributed systems split-brain / zombie-worker hazard).

## Solution

**GhostShift** (incorporating the **RELAY** paid-takeover flow) is a NEAR Protocol on-chain monotonic epoch-fencing, lease takeover, and verifiable settlement workbench built for **NEAR Hackathon 2026** (`tracks: ["security", "swarms", "agents", "business", "open"]`). It combines four core NEAR primitives into an inseparable closed loop:
1. **NEAR Smart Contract (`near-sdk v5.29.x`) with Monotonic `Epoch` Fencing & `Yield & Resume` (`env::promise_yield_create` / `env::promise_yield_resume`)**: Every lease claim or failover takeover increments a strictly monotonic `epoch: u64` fencing token on-chain. Submitting a result pauses the contract via `promise_yield_create` (~200-block window) until the verifier resumes it via `promise_yield_resume`, and any write or callback carrying `epoch < current_epoch` is deterministically rejected on-chain (`StaleEpochRejected`) even if signed by a previously authorized worker key.
2. **Hierarchical Sub-Accounts & Scoped Function-Call Access Keys**: Each worker agent (`worker-a.ghostshift.testnet`, `worker-b.ghostshift.testnet`) operates under a dedicated sub-account with a scoped Function-Call Access Key restricted to the coordinator contract and explicit method allowlist (`claim_lease`, `heartbeat`, `takeover_lease`, `submit_result`), preventing direct `NEAR` transfers or key escalation.
3. **NEAR AI Cloud Hardware-Attested Verification (`https://cloud-api.near.ai/v1`)**: Handoff diagnosis and deliverable verification run inside Intel TDX + NVIDIA NRAS confidential hardware, verifying the attestation report (`/v1/attestation/report`) and per-chat cryptographic signature (`/v1/signature/{chat_id}`) against the enclave's `signing_address` before resuming the yielded contract.
4. **NEAR Intents 1Click Cross-Chain Settlement (`https://1click.chaindefuser.com/v0/quote`, `dry: true`)**: Once the current epoch holder's deliverable is accepted (`Completed`), the contract locks the winner and requests a real 1Click cross-chain swap quote (`dry: true` preview or live status state machine) to settle the bounty in the winning worker's preferred destination asset (e.g., USDC on Base, Arbitrum, or Solana) at most once per job.

## Implementation Decisions

- **Rust Smart Contract (`contracts/ghost-shift/src/lib.rs`, `near-sdk v5.29.x`) & Isomorphic TypeScript State Machine (`src/engine/ghost-shift-engine.ts`)**:
  - Both the Rust contract and the isomorphic TypeScript state machine implement the exact same transition rules and integer `yoctoNEAR` / integer-cent accounting (zero floating-point math) `[evidence: scratchpad/near-hackathon-2026-ideation-prompt.md Section 2]`
  - Job lifecycle states: `Open` → `Leased(epoch, holder, leaseExpiresAtMs)` → `YieldPending(epoch, holder, candidateResultId, yieldId, yieldDeadlineBlock)` → `Completed(winningEpoch, winningWorker, acceptedResultId, paidAmount)` or `Refunded(refundedTo, refundedAmount)` `[inferred]`
  - Every mutating worker action (`heartbeat`, `submit_result`) requires the caller's explicit `epoch: u64` and `workerId: string`. If `job.status` is `Completed` or `Refunded`, any further `claim_lease`, `heartbeat`, `takeover_lease`, `submit_result`, or `resume_verify` is rejected with `TerminalStateImmutable`. If `epoch < job.currentEpoch` or `workerId !== job.activeHolder`, the action is rejected with `StaleEpochRejected` and appended to the immutable `rejectedStaleAttempts` audit log without mutating the accepted result or balances `[user: "ok"]`
  - Calling `takeover_lease` before `nowMs >= job.leaseExpiresAtMs` is rejected with `LeaseStillActive`. Calling `takeover_lease` when `nowMs >= job.leaseExpiresAtMs` while in `Leased` (or after a `YieldPending` timeout at `currentBlock >= yieldDeadlineBlock`) increments `currentEpoch += 1`, assigns `activeHolder = newWorkerId`, extends `leaseExpiresAtMs = nowMs + leaseDurationMs`, and clears any timed-out yield ticket `[evidence: /Users/linhancheng/Downloads/near-hackathon-2026-ideas (1).md GhostShift]`
  - Calling `submit_result` with the current valid `(epoch, activeHolder)` transitions the job to `YieldPending`, creates a `yieldId` (`env::promise_yield_create` in Rust with `#[private]` callback `on_verify_settled`), and waits for `resume_verify(yieldId, epoch, verdict, teeAttestation)`. If `resume_verify` arrives after `yieldDeadlineBlock` (200-block timeout) or with `verdict = Reject`, the job either returns to `Leased` (if lease time remains) or allows `takeover_lease` / `cancel_expired_job` so escrowed funds are never permanently locked `[evidence: /Users/linhancheng/Downloads/near-hackathon-2026-ideas (1).md line 9]`
- **Scoped Function-Call Access Key & Sub-Account Guard (`src/engine/access-key-guard.ts`)**:
  - Models and validates NEAR sub-account identities (`worker-a.ghostshift.testnet`, `worker-b.ghostshift.testnet`, `verifier.ghostshift.testnet`) and their `FunctionCallPermission` (`receiverId`, `methodNames`, `allowanceYocto`). Any attempt by a worker key to invoke `DeleteAccount`, `Transfer`, `AddKey`, `DeployContract`, or an unwhitelisted contract method (`resume_verify` called by a worker key instead of `verifier.ghostshift.testnet`) is deterministically blocked with `ScopedKeyPermissionDenied` `[evidence: scratchpad/near-hackathon-2026-ideation-prompt.md Section 2.4]`
- **NEAR AI Cloud TEE Attestation & Signature Verifier (`src/verifier/near-ai-tee.ts`)**:
  - Connects to `https://cloud-api.near.ai/v1` (`GET /v1/attestation/report?model=...`, `POST /v1/chat/completions`, `GET /v1/signature/{chat_id}`) when `NEAR_AI_API_KEY` is configured, and provides a deterministic offline cryptographic verification fixture (`secp256k1` / `ecrecover` message-signature + 64-hex-char nonce binding check across Intel TDX `report_data` and NVIDIA NRAS `eat_nonce`) so `npm run verify:judge` works both with live credentials and in zero-secret CI/judge environments (explicitly labeling `LIVE_TEE` vs `DETERMINISTIC_FIXTURE` provenance, never faking live status when offline) `[evidence: /Users/linhancheng/Downloads/near-hackathon-2026-ideas (1).md line 128]`

## Testing Decisions

- **What makes a good test**: Tests invoke only the public state machine and verification seams (`applyGhostShiftAction`, `evaluateGhostShiftOracle`, `verifyScopedFunctionCallKey`, `verifyTeeSignatureEnvelope`, `runJudgeVerificationSuite`) and assert observable state transitions, balances, rejection codes, and invariant verdicts without mocking internal state helpers `[user: "ok"]`
- **Modules under test**:
  - `src/engine/ghost-shift-engine.ts` & `contracts/ghost-shift/src/lib.rs` (monotonic epoch fencing, lease expiry takeover, `Yield & Resume` lifecycle, integer balance conservation);
  - `src/engine/ghost-shift-oracle.ts` (independent sequential reference oracle for `P1..P4`);
  - `src/engine/access-key-guard.ts` & `src/verifier/near-ai-tee.ts` & `src/intents/oneclick-quote.ts`;
  - `src/verifier/judge-audit-runner.ts` (`npm run verify:judge` end-to-end report generator).
- **Prior art**: Node 24 native test runner (`node --experimental-strip-types --test`) + `fast-check` 3-Role Conditional PBT pattern from `atlassian-clause-clock`, `qnx-vss-warden`, and `vultr-chart-truth`.
- **Conditional PBT Specification (Shape 1 — Multi-Step Interlocking State Machine & Conservation Invariants)**:
  - **Applicability domain**: Action sequences of length `1..30` generated over 1..3 jobs (`bountyAmount` in integer units `1_000..1_000_000_000`, `leaseDurationMs` in `1_000..60_000`, `yieldTimeoutBlocks = 200`), 3 worker sub-accounts (`worker-a`, `worker-b`, `worker-c`), and 1 verifier account (`verifier`), mixing valid actions with adversarial race actions (`SubmitResult` with stale `epoch < currentEpoch`, early `TakeoverLease` before expiry, duplicate `ResumeVerify`, late `ResumeVerify` after 200 blocks, and actions after `Completed`/`Refunded`).
  - **Independent Oracle boundary**: `evaluateGhostShiftOracle(initialState, actionTrace, currentState)` replays the action trace against a separate event-sourced ledger specification (tracking active epoch, rightful lease holder, terminal lock, and fund conservation from first principles without importing or calling `applyGhostShiftAction`) and checks `P1..P4` after *every individual step*.
  - **Mapped Invariants (`P1..P4`)**:
    - **`P1` (Monotonic Epoch & Single Holder Exclusivity)**: Across every step for a given `jobId`, `nextState.currentEpoch >= prevState.currentEpoch`, `currentEpoch` increments by `1` on each valid `ClaimLease` / `TakeoverLease`, and at most one `activeHolder` holds write authority for a given `(jobId, currentEpoch)`.
    - **`P2` (Stale-Epoch & Unauthorized Write Immunity)**: Any `Heartbeat`, `SubmitResult`, or `ResumeVerify` carrying `epoch !== currentEpoch`, a non-holder `workerId`, or an unverified TEE signer never mutates `acceptedResultId`, `winningWorker`, `currentEpoch`, or account balances, and is recorded as a rejected attempt (`StaleEpochRejected` / `UnauthorizedSigner`).
    - **`P3` (At-Most-Once Payout & Exact Fund Conservation)**: Each `jobId` transitions to `Completed` and credits a payout at most once across the entire trace; at every step, `escrowedLocked + totalPaidOut + totalRefunded === totalFunded` holds in exact integers (`0` floating-point drift).
    - **`P4` (Terminal Finality & Yield-Timeout Liveness)**: Once a job reaches `Completed` or `Refunded`, its `status`, `winningEpoch`, `winningWorker`, `acceptedResultId`, and payout/refund amounts remain invariant under any subsequent action; and if a `YieldPending` state exceeds `yieldDeadlineBlock` (200 blocks), `YieldTimeout` cleanly unlocks the job so funds are never permanently trapped in `YieldPending`.
  - **Three Test Roles**:
    - **Role 1 (Concrete Capability Examples)**: Verifies happy-path claim → submit → TEE verify resume → 1Click quote preview; early takeover rejection (`LeaseStillActive`); zombie worker stale-epoch rejection (`StaleEpochRejected`); 200-block yield timeout recovery + refund; and scoped Function-Call Key permission enforcement.
    - **Role 2 (Safety Property Guardians `fc.property` + Reachability Witnesses)**: Evaluates `P1..P4` after every step of randomized 30-step action sequences (`200` runs), returning `false` immediately on any `Pi` violation, and asserts aggregate `reachabilityWitnesses` (`takeoverExecutedCount > 0`, `staleEpochBlockedCount > 0`, `yieldTimeoutRecoveredCount > 0`, `completedSettlementCount > 0`) after `fc.assert` completes.
    - **Role 3 (Oracle Calibration & Counterexample Replay)**: Calibrates each `P1..P4` check individually in test-local controls (verifying a test-local non-monotonic epoch mutation trips `P1`, a test-local unfenced stale-write mutation trips `P2`, a test-local double-payout mutation trips `P3`, and a test-local post-terminal overwrite mutation trips `P4` without adding fault switches to production code), and pins a deterministic shrunken counterexample trace demonstrating how an unfenced coordinator suffers split-brain overwrite + double payout on `[Claim(A, e=1), Expire, Takeover(B, e=2), Submit(B, e=2), Resume(e=2), LateSubmit(A, e=1)]` while `GhostShift` preserves `B`'s settlement.

## Out of Scope

- Claiming global `exactly-once` side effects on arbitrary third-party external Web2 APIs (such as sending emails or placing external HTTP orders) that do not check the on-chain `epoch` fencing token.
- Executing irreversible mainnet token swaps during automated judge runs (`1Click` integration uses `dry: true` real quote previews + Testnet state settlement per `HACKATHON.md` `Q-007` and `Q-010`).
- Generic wallet spending caps or counterparty scam blocklists (already saturated by 13+ competing hackathon repos).
